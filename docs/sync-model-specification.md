# LingoFlow 同步数据模型规范

本文档定义 LingoFlow 用户数据模型的长期架构原则，适用于本地持久化、备份、迁移以及未来可能引入的云同步能力。它不记录版本历史、开发阶段、当前实现状态或交付计划。

## 1. Design Principles

- LingoFlow 保持 local-first。用户应能在没有网络或云服务的情况下使用核心功能，本地数据是日常读写与产品体验的基础。
- 未来云同步建立在稳定、清晰且可迁移的本地数据模型之上。同步是本地数据能力的扩展，不替代本地持久化，也不应成为核心功能可用的前提。
- 优先保证用户数据的身份、生命周期、一致性和可恢复性，再引入跨设备传输与冲突处理能力。
- 在需求和边界明确前，不提前引入后端、账号系统或复杂同步依赖。
- 区分用户不可轻易重建的资产与可重新下载或生成的资源，避免用同一套同步和备份策略处理两者。

## 2. Entity Model

### Article

- Article 是独立的用户资产，具有不依赖标题、正文或来源内容的稳定身份。
- Article 的生命周期至少需要覆盖创建、内容或元数据更新、软删除、恢复与安全清理。
- 用户个人文章记录与原始内置来源身份应明确区分。来源信息可以建立关联，但不能替代个人文章的身份。
- Article 被删除时，不应级联删除 Favorite、QueryEvent 或其中保留的内容快照。关联方应能安全表达原文章已不存在。
- 重要正文发生冲突时，应优先避免静默覆盖用户内容。

### Reading Progress

- Reading Progress 依附于 Article，是 Article 的阅读状态，不作为具有独立身份的同步实体。
- Reading Progress 可以拥有独立于文章内容更新时间的进度更新时间，以避免阅读行为被误判为正文修改。
- 历史最高进度与当前阅读位置具有不同语义：最高进度表示用户曾经到达的最远位置，通常单调不减；当前位置表示用户下一次希望继续阅读的位置，可以前进或后退。
- 冲突处理不得仅因历史最高进度更大，就用它覆盖更符合用户最近阅读行为的当前位置。

### Favorite

- Favorite 是独立的核心用户资产，需要不依赖收藏内容的稳定身份。
- Favorite 应明确区分单词与词组，并保留对用户有价值的内容快照，例如展示文本、释义、上下文、备注或标签。
- Favorite 可以弱关联来源 Article，但文章关联与内容快照必须保持清晰边界。来源删除或不可访问时，内容快照仍应可用。
- 复习、掌握度等学习算法状态应与 Favorite 内容解耦。相关能力应通过 Favorite 的稳定身份关联独立的学习进度数据层。
- Favorite 的删除需要支持跨设备传播，不能仅依赖从本地集合中物理移除记录。

### QueryEvent

- QueryEvent 是对一次查询行为的不可变事实记录，具有稳定且不复用的事件 ID。
- 事件应保留表达该次查询所需的事实信息，包括事件发生时间；来源、设备信息或查询结果快照按实际需求记录。
- 已写入的事件不通过原地修改来表达新的查询事实。重复传输的同一事件应由稳定 ID 去重。
- QueryEvent 集合是查询历史的事实来源。查询次数、最近查询、来源统计等聚合数据属于可重新计算的派生视图，不应成为另一份独立事实。

### Preferences

- Preferences 表示用户可持久化的阅读、发音及其他产品设置。
- 可跨设备复用的用户偏好与设备本地状态应明确区分，避免把设备 ID、权限状态、硬件能力或仅在本机可用的资源选择直接当作通用用户偏好同步。
- Preferences 的冲突与更新应按设置项处理，避免一个设置项的变化覆盖整组无关设置。

## 3. Identity Rules

- 可独立同步的实体必须具有稳定身份；依附实体可以由其所属实体和明确的结构边界确定身份。
- ID 不依赖标题、正文、单词文本、规范化内容、列表位置或可变业务字段。
- ID 在实体创建时确定，并在更新、删除、恢复、迁移和设备间传输时保持不变。
- 已删除实体的 ID 不得分配给新的实体，以免旧 tombstone 或延迟到达的数据作用于错误对象。
- 实体引用应使用稳定身份，并允许安全处理目标已删除、尚未到达或暂时不可用的情况。
- 外部来源身份与用户实体身份属于不同命名空间和生命周期，不应相互替代。

## 4. Time Model

不同实体具有不同的时间语义，不要求所有实体机械地包含完全相同的时间字段。

- `createdAt` 表示实体首次创建的时间。对于具有生命周期的用户资产，该时间在后续更新中保持稳定。
- `updatedAt` 表示可变实体的内容或元数据最近一次发生有效修改的时间。一个实体内部语义独立的状态可以拥有自己的更新时间。
- `deletedAt` 表示实体进入软删除状态的时间，并承担 tombstone 生命周期中的删除时间语义；恢复时应按明确规则撤销删除状态。
- event timestamp 表示不可变事件实际发生的时间，不等同于可变实体的 `updatedAt`。
- 时间字段不能代替稳定 ID，也不应被当作适用于所有实体和所有冲突的唯一裁决依据。
- 持久化时间应使用跨设备可解析、语义明确的一致表示，并对缺失或不可信的旧数据采取保守处理。

## 5. Deletion Model

- 需要同步的用户资产原则上采用 soft delete，使删除可以恢复并传播到其他设备。
- 软删除记录在删除状态保留期间仍保持原稳定身份；恢复应作用于同一实体，而不是创建身份不同的替代记录。
- tombstone 用于表达某个稳定身份已被删除，并保留安全传播和冲突判断所需的最小信息。
- 删除与并发更新发生冲突时，不得无提示复活已删除数据，也不得无提示丢弃重要用户修改。
- 最终清理必须具有明确且可验证的安全边界，包括同步传播、恢复窗口和备份影响。
- 在无法安全传播删除状态前，不得自动永久清除同步相关数据。
- 不可逆的永久删除或批量清空应具有明确的用户确认边界。

## 6. Conflict Principles

冲突策略按实体语义选择，不使用一套全局规则处理所有数据。

### Article

- 避免自动覆盖重要正文或用户编辑。
- 无法安全自动合并时，应保留可恢复的信息，并为后续明确处理保留边界。
- 来源元数据、阅读状态与正文内容不应因为共享同一 Article 而被视为同一种冲突。

### Favorite

- 以稳定身份进行记录级冲突判断。
- 不同 Favorite 作为独立记录合并；同一 Favorite 的内容、备注和删除状态按照各自语义处理。
- 冲突处理不得因为来源 Article 缺失而丢弃已经保存的内容快照。

### Reading Progress

- `maxProgress` 与 `currentPosition` 分开处理。
- `maxProgress` 可以按单调历史进度合并；`currentPosition` 应反映合理的最近阅读位置，不能由最大值简单替代。
- 阅读进度冲突不应修改 Article 正文或其他内容元数据。

### QueryEvent

- 通过稳定事件 ID 对集合取并集并去重。
- 同一事件的重复传输不产生新的查询事实。
- 聚合视图在事件集合变化后重新计算，不参与事实层冲突合并。

### Preferences

- 按设置项确定冲突边界，不以整个设置对象作为不可分割单元。
- 设备本地设置不参与通用用户偏好合并。
- 不同设置项可以采用不同决策规则，但必须保持确定性并避免覆盖无关设置。

## 7. Migration Principles

- IndexedDB 等存储引擎的数据库版本与业务数据的 Schema Version 分离管理；两者只在各自确有变化时推进。
- 迁移步骤应可识别、可重复执行，并能在中断后安全恢复。只有在相关写入完整成功后，才记录迁移完成。
- 迁移不得以空默认值或新结构无提示覆盖仍可恢复的用户数据。
- 对缺失字段、重复记录、旧身份方式和部分迁移状态采用明确且保守的兼容策略。
- 不把旧聚合数据伪造成从未发生过的历史事件。必要时可以保留明确标识的迁移基线或兼容记录。
- 迁移应尽可能保留用户可理解的内容和语义，同时避免为了历史兼容显著增加长期架构复杂度。
- 不承诺无限历史兼容。无法低成本安全迁移的数据，应通过明确的支持边界、恢复路径或用户提示处理。

## 8. Rebuildable Resources

以下内容属于可重新下载、导入或生成的资源，不属于用户同步资产：

- dictionary data
- lemma mapping
- dictionary metadata

这些资源不应进入核心用户同步模型，也不应成为普通个人数据迁移的必要负担。高级离线迁移或故障恢复可以单独处理它们，但不能因此模糊用户资产边界。

## 9. Long-term Boundaries

为未来同步准备数据模型，不代表当前架构需要提前引入以下能力：

- 后端服务器
- 登录或账号系统
- 实时同步
- CRDT
- 复杂冲突 UI

除非后续经过明确设计，这些能力不构成本规范的前置条件。核心本地数据访问、迁移和产品功能应保持不依赖网络传输、远端账号或特定同步服务。

本规范定义实体语义和长期数据边界，不指定云服务提供方、网络协议、认证方式、服务端存储、传输调度或最终冲突界面。
